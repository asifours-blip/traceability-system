# 业务闭环：归属、交接、校验、更正与公开视图

生产 → 分销 → 零售 → 消费者扫码。链上成功以回执为准（见 [tx-lifecycle.md](tx-lifecycle.md)）；本文区分 v2/v3 的链上规则、后端业务规则和各自的验证边界。

## 链上规则与后端规则的边界（先读这一节）

| 规则 | v2 批次 | v3 批次 |
|------|---------|---------|
| 角色、生产 → 分销 → 零售顺序、每阶段只写一次 | 合约强制 | 合约强制，保留 v2 约束 |
| 只有被指定的下游能写下一阶段 | **只由后端校验**；持角色账户直调 v2 合约可绕过 | 合约校验调用者等于当前链上指定地址，且指定对象持对应角色；后端仍先校验并给友好错误 |
| 生产者在分销前改派分销商 | 后端 `trace_assignment_log` 留痕 | 生产者发 `redesignateDistributor` 链上交易并留事件；分销写入后不可改 |
| 分销商在零售前改派零售商 | 现有后端链下流程 | **不支持**；v3 设计和合约均无零售改派接口 |
| 批次归属、业务字段校验、链下更正 | 后端；直接读链仍可见公开链上数据 | 同左；合约不验证证书/质检报告内容真实性 |

v2 的旧真实链业务流中，outsider 已持分销商角色，却是后端返回 403；这**不能**证明 v2 合约会拒绝它。v3 裸链测试绕过后端直调合约：两次运行的非指定分销商交易在块 42、59 回执 `status=0x16`，revert 为 `Trace: caller is not the designated distributor`；对应证据见 [产物索引](artifacts/README.md)。v3 后端版本分流的六笔交易块 77–82 均回执 `0x0`，目标地址与批次版本匹配，读模型与消费者三阶段查询通过；该次业务库是 H2 内存、文件服务是 FakeKubo，**不是**真实 MySQL/IPFS 业务全链路验证。

应用按批次绑定的版本和合约地址选择 ABI。新批次用 v3；已有 v2 批次固定原实际 v2 地址并在 v2 继续流转，不中途换合约。迁移 SQL 必须先填真实 v2 地址；运行时配置只有一份 v2、一份 v3 地址，和批次绑定地址不一致时拒绝读写，**不支持多历史地址自动路由**。链上指定地址可由 `getDesignations` 查询；MySQL 保存账号、企业名与交接历史。WeBASE-Front 托管私钥仍需部署隔离，见 [生产边界](production-boundaries.md)。

## 数据表（`db/business-schema.sql`）

| 表 | 作用 |
|----|------|
| `trace_batch` | 溯源号 → 建档生产商、当前指定下游账号、绑定的合约版本与地址；溯源号唯一 |
| `trace_assignment_log` | 每次指定/变更交接对象的历史（原对象、新对象、操作人、原因、时间），只追加 |
| `trace_correction` | 链下更正：阶段、提交人（及其链上地址快照）、原因、`{字段: 更正值}`、时间；应用不提供修改/删除接口 |
| `account_role_grant` | 业务账号的链上授权状态：`GRANTED_BY_TX` / `ALREADY_ON_CHAIN` / `PENDING` |

## 归属与交接

- **生产**（`POST /producer/add`）：必须带 `distributorUsername`（启用中的分销商账号）。先读链：溯源号已在链上 → 409，不占用。否则插入 `trace_batch`（唯一索引兜底并发）并记首次指定历史，再发交易。同一生产商在交易失败或查证「未写入」后可以重新提交；别的生产商用同一溯源号 → 403。
- **分销**（`POST /distributor/add`）：只有 `trace_batch.distributor_id` 是当前账号才放行，否则 403；还要求链上生产阶段的写入者就是本批次的生产商（防止链下归属与链上事实不一致）。请求必须带 `retailerUsername`，写入零售商指定。
- **零售**（`POST /retailer/add`）：只有 `trace_batch.retailer_id` 是当前账号才放行。
- **变更交接对象**：v2 沿用 `PUT /batches/{tn}/distributor`（生产商）与 `PUT /batches/{tn}/retailer`（分销商）的链下流程；v3 仅允许生产商在分销前通过 `PUT /batches/{tn}/distributor` 发起链上 `redesignateDistributor`，零售改派请求被拒绝。对应阶段已写入或有未决交易时拒绝，改派留链上事件与链下历史。
  - v3 设计只允许生产者在分销写入前改派分销商；不能据此推导出零售改派能力。
- **并发**：写入侧在 `chain_tx` 占住业务键之后、发请求之前执行 guard，加锁重读 `trace_batch` 确认当前用户仍是被指定者；变更侧先条件更新、再在同一事务里检查未决交易，失败回滚。这是原 v2 链下台账的事务约束；v3 指定对象以链上状态和交易回执为最终裁决，不能把跨 MySQL 与链交易描述成原子提交。
- **可见性**：`GET /batches` 生产商看自己建档的、分销商/零售商看指定给自己的、管理员看全部；`GET /batches/{tn}` 只有这三方与管理员能看，其余 403。列表分页（`page` / `size` / `todo` / `keyword`），归属取 `trace_batch`、链上进度取读模型（[read-model.md](read-model.md)），不逐条读链；详情再读链。
- **历史数据**：本功能上线前直接写在链上的批次没有 `trace_batch` 记录。管理员「重建读模型」时按 `getStageActors` 的写入者地址匹配对应角色的账号回填归属与交接历史；匹配不上的标为「未认领」（或某阶段写入者对不上时为「部分认领」），列在管理员页面，补建账号后再重建即可认领。见 [read-model.md](read-model.md)。

## 字段校验（HTTP 400，逐字段）

响应体 `{"code":400,"mes":"参数校验失败：saleQuantity 不能超过分销数量（500）（共 2 处错误）","data":{"errors":[{"field":"saleQuantity","message":"…"}, …]}}`。请求体解析失败（如数量传 `"abc"`）同样返回 400 并尽量指出字段。

| 规则 | 说明 |
|------|------|
| 溯源号 | `^[A-Z][A-Z0-9-]{3,63}$`。仓库原来**没有生成规则**（生产商手填）；已有样例 `SY60202600001`（IoT 模拟批次）、`LC-3`、`E2E-…` 都符合。会出现在二维码 URL 路径里，所以不允许小写、空格、斜杠。前端「生成」按钮按 `SY + yyyyMMdd + - + 4 位随机数` 生成 |
| 必填 | 三个阶段全部字段；文本 ≤ 64（地址类 ≤ 200）；CID 只能是字母数字 |
| 数量、价格、保质期 | 正整数，≤ 10¹²。DTO 用 `BigDecimal` 接收：Jackson 默认会把 `10.5` 静默截断成 `Long 10` |
| 日期 | `yyyy-MM-dd`（严格解析，`2026-02-30` 不通过），不晚于今天（Asia/Shanghai） |
| 零售数量 ≤ 分销数量 | 分销数量从链上读 |
| 日期不早于上一阶段 | 分销阶段没有业务日期字段（合约里只有上链时间），所以零售的销售日期与链上的生产日期比较 |

## 重复提交与状态

沿用 `chain_tx` 业务键：同一溯源号同一阶段有未决交易时再提交 → 409，data 是那条未决记录。批次详情的每个阶段给出：

| status | 含义 | 前端 |
|--------|------|------|
| `NOT_STARTED` | 没有交易记录 | 未开始 |
| `PENDING` | 最新记录 PENDING/SUBMITTED/UNKNOWN 且占着业务键 | 待确认 + 「查证」按钮（`POST /chain-tx/{id}/verify`，签名者本人或管理员） |
| `RELEASED` | UNKNOWN 但查证确认当时未写入，业务键已释放 | 可重新提交 |
| `CONFIRMED` | 有成功记录 | 已上链 + 交易哈希与块高（读链查证确认的没有哈希） |
| `FAILED` | 最新记录失败 | 失败原因 |

另有 `onChain`（链上是否已有该阶段数据）与 `writer`（链上写入者地址），链暂时读不到时返回 `chainError`，不拿链下数据冒充。

前端超时：普通请求 5 秒；上链、查证、建号、系统信息写入单独 60 秒（WeBASE `transMaxWait` 约 30 秒 + 后端读超时 40 秒 + 前后只读调用）。前端等待超时按「结果未知」提示，引导到批次详情查证，不提示失败。

## 链下更正

`POST /batches/{tn}/corrections`，body `{"stage":"DISTRIBUTION","reason":"…","content":{"distributeQuantity":"1000"}}`。

- 只有该阶段的**链上写入者本人**（`getStageActors` 读出的地址 = 当前账号绑定地址）能提交；阶段未上链 → 409。
- 字段必须属于该阶段，值按同样的字段规则校验。
- 只追加：没有修改、删除接口（测试里断言 PUT / DELETE 返回 4xx）。数据库层面没有加触发器；生产环境建议给应用账号收回 `trace_correction` 的 UPDATE / DELETE 权限。
- 消费者页展示链上原始值，旁边标「链下更正：新值」，悬停看原因、提交企业与时间；只展示公开字段的更正。

## 消费者扫码页与公开字段

`GET /trace/detail/{tn}`（免登录）改为只返回公开字段。改动前它返回了三个阶段的全部字段，包括价格、数量、仓库地址、单据号和证书/报告的 CID；链上地址当时没有返回（`getStageActors` 只在后端内部用）。

| 阶段 | 公开 | 不公开 |
|------|------|--------|
| 生产 | 生产企业、产品名称、产地、品种、生产批次、生产日期、上链时间、是否有认证图片 | 认证 CID |
| 分销 | 分销企业、存储条件、运输方式、上链时间、是否有质检报告 | 分销批次、仓库地址、分销价格、分销数量、质检报告 CID |
| 零售 | 零售企业、保质期、销售日期、上链时间 | 零售价格、零售数量、单据号 |
| 其他 | 各阶段交易哈希与块高、公开字段的链下更正（原因、提交企业、时间） | 链上地址、用户名 |

判断依据：B2B 价格和数量是商业信息；仓库地址涉及安全；单据号可能关联交易对手；CID 一旦公开就能绕过「只读已绑定文件」的限制。**以下是待确认项**：

1. 零售价格：消费者在货架上本来就能看到，公开也合理；目前按「不公开」处理。
2. 分销批次号：敏感度低，目前不公开。
3. 交易哈希与块高：本系统是联盟链，消费者无法自己去链上核对，公开它只起「有凭据」的展示作用；目前公开。
4. 更正里的提交企业名：目前公开（企业名在原始记录里本来就公开）。

字段清单在后端 `TraceFields`（`isPublic`）与前端 `utils/traceFields.js` 各一份，改动时两边一起改。

## 证书与质检报告图片

- 新增 `GET /trace/{traceNumber}/file/{stage}`（免登录），`stage` 只能是 `production`（生产认证）或 `distribution`（质检报告）。CID 从链上该溯源号该阶段的字段读出，调用方不能指定 CID；阶段未写入或没有绑定 → 404；按文件头判断图片类型，识别不了按 `application/octet-stream`，并加 `X-Content-Type-Options: nosniff`。
- 原来的 `/file/{hash}`、`/fileBase64/{hash}` 仍需登录：任意 CID 不能匿名读取。
- 限制：已登录的任何账号仍能按 CID 读任意文件（原有行为，未收紧）。

## 建号幂等

`POST /admin/users`：

1. 先读链 `isProducer / isDistributor / isRetailer`：已有该角色 → 不发授权交易，直接建号并启用（`ALREADY_ON_CHAIN`）。
2. 没有 → 管理员签名发 `addX`：回执成功 → 建号启用（`GRANTED_BY_TX`）；明确失败或未发出 → 不建号。
3. 结果未知（202）→ 建号但**保持停用**，状态 `PENDING`，响应 202。管理员在列表点「查证」（`POST /admin/users/{id}/verify-role`：先查证交易，再以链上 `isX` 为准，有角色才启用）或「重试授权」（`POST /admin/users/{id}/grant-role`：链上已有角色就不再发交易）。

## 前端

| 页面 | 改动 |
|------|------|
| 生产商 `/producer` | 建档表单必须选下游分销商；溯源号自动大写、可生成；上链按钮显示等待回执；按 200/202/409/400/超时 分别提示，并跳到批次详情；下方是「我建档的批次」 |
| 分销商 `/distributor`、零售商 `/retailer` | 只列指定给自己的批次（可筛「待我处理」，筛选条件在 URL 里）；录入在批次详情里完成 |
| 批次详情 `/batch/:traceNumber?stage=` | 新页面：三方与交接历史、每阶段状态（未开始 / 待确认 / 已上链 + 哈希与块高 / 失败原因）、查证按钮、链上原始数据与图片、更正列表与追加入口、分销/零售录入表单（只对被指定者显示，后端同样校验）、变更交接对象 |
| 溯源档案 `/traceList` | 改用 `/batches`，不再调已删除的 `/trace/list` |
| 消费者 `/traceDetail/:tn` | 只显示公开字段、链下更正标注、图片走公开文件接口、交易凭据；未登录时不再请求需要登录的 IoT 接口 |
| 溯源查询 `/trace` | 修掉 `v-model.number`（溯源号是字符串） |
| 用户管理 | 链上授权状态列；202 提示；待确认账号的「查证」「重试授权」 |
| 登录 | 登录过期跳 `/login?redirect=原地址`，登录后回到原页面（只接受站内相对路径） |

`request.js` 对 4xx/5xx 不再统一吞成「服务器错误」，一律返回 `{code, mes, data}` 交给页面处理。
